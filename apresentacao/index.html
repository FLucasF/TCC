o que é um design pattern

Um design pattern organiza o que varia novo caso: plano Premium

com condicional
double preco(String plano, double base) {  if (plano.equals("BASICO")) return base;  if (plano.equals("PLUS"))   return base * 0.9;  if (plano.equals("PREMIUM")) return base * 0.8;} int limite(String plano) {  if (plano.equals("BASICO")) return 1;  if (plano.equals("PLUS"))   return 3;  if (plano.equals("PREMIUM")) return 10;}
com Strategy
interface Plano {  double preco(double base);  int limite();}class Basico implements Plano { ... }class Plus   implements Plano { ... }class Premium implements Plano {  double preco(double b) { return b * 0.8; }  int limite() { return 10; }}
mexe em todo lugar que pergunta qual é o plano
uma classe nova; o código que já funciona não muda

em outras palavrasUm design pattern é uma forma conhecida de organizar o código para que o próximo caso entre sem mexer no que já funciona.

Gamma et al. (1995); Fowler (2018). Exemplo simplificado.

Clique 1: chega um novo caso. Clique 2: na condicional, é preciso mexer em vários lugares. Clique 3: no Strategy, só entra uma classe nova.
o risco oposto

Usar o pattern onde ele não se justifica também é um problema

Seguro por região: só a porcentagem muda de uma região para outra (valores ilustrativos).

certo · um valor por região

Norte → 2% · Sul → 1% · Sudeste → 1,5%
dados ou uma condicional simples

exagero · uma estrutura por região

SeguroNorte, SeguroSul, SeguroSudeste…
classes que nada acrescentam

A flexibilidade custa indireção [Gamma et al. 1995]; Fowler (2018) chama isso de generalidade especulativa. Neste trabalho: exagero.

O risco oposto: aplicar a técnica onde ela não é necessária. Por isso o experimento tem um ponto de controle, o seguro.

Acerto é isolado e consulta, ou isolado e condicional única. Espalhado, ou condicional no cálculo, é erro. As respostas valem para os quatro pontos com variação; o seguro tem duas perguntas próprias, a forma e a proporção.

As 10 regras de cada ponto

Cada regra procura uma forma de escrever e marca a linha; a decisão do que isso significa é de outro script, o classificador.

regraa ideiaexemplocomo entra na resposta
cond-calcuma comparação que nomeia um casonivel == OURO, "OURO".equals(x)candidata a condicional no cálculo; sai da conta se for recusa ou fábrica
cond-validacaoa mesma comparação, dentro de um if que recusa com throwif (nivel == OURO) throw …conta como espalhado, mas não na escolha do caso
cond-recusaa mesma comparação, num if que devolve um erro, sem throwif (…) return erroo mesmo da validação
cond-fabricaa mesma comparação, num if que só devolve ou guarda um objetoif (…) return new Ouro()condicional única
instanceofinstanceof de uma classe de caso, fora do equals()x instanceof NivelOuronomeia o caso, como a comparação
instanceof-recusao mesmo, dentro de um if que recusaif (x instanceof NivelOuro) throw …conta como recusa
switch-labelum rótulo de switch que nomeia um caso, inclusive com pattern matchingcase OURO, case Ouro onomeia o caso
switch-fabricao rótulo que só devolve um objetocase OURO -> ourocondicional única
conjuntoum conjunto ou lista que cita casosEnumSet.of(OURO)só conta se não citar todos os casos
nomeo alarme: o nome do caso aparece em algum lugar?—sem nenhum nome, o ponto sai indeterminado, e não isolado
As mesmas dez regras valem para o frete, o cupom, o pagamento e o clube; muda só a lista de nomes dos casos. Umas regras entendem o código (um if, uma comparação, um new), e outras são buscas de texto, para o que o analisador não vê bem, como o case com pattern matching.

O seguro é o controle negativo: as regras procuram a forma da variação, e o classificador decide se é dado ou estrutura.

Estrutura é o exagero que o seguro mede: uma classe por região, uma constante com corpo, uma função por região, ou um switch ou mapa que devolve um objeto por região. Lista de objetos da mesma classe, só com os números, é uma tabela, ou seja, dados.

O que não conta como caso, e como as regras foram testadas

O que não conta

a recusa: um if que só devolve um erro

a lista de válidos: um bloco que cita todos os casos só para conferir

o registro: a classe Ouro dizendo que atende "OURO"

os nomes em inglês contam como o mesmo caso: GOLD é OURO

se nenhum nome aparece, a resposta é indeterminado, e o ponto fica fora da conta

Como foram testadas

quatro conjuntos de projetos pequenos, cada um com uma só forma de escrever e a resposta escrita antes de rodar as regras

desenvolvimento: a primeira versão acertou 41 de 80; a segunda, 80 de 80

controle, com formas novas: 42 de 44 na primeira passada e 44 de 44 depois de corrigir as duas falhas previstas

em 64 projetos reais, só 3 respostas mudaram da primeira para a segunda versão, e as três foram conferidas no código

Uma forma de escrever que ninguém previu ainda pode passar; por isso uma pessoa conferiu 44 execuções, às cegas.

Esses números são da validação das regras, feita antes da coleta, e estão no README da pasta do Semgrep. O que vale como validação final é a conferência humana: 174 de 176 respostas iguais.

limitações

O que estes resultados não dizem

  • Só modelos da Anthropic e um só agente, o Claude Code.
  • Na extensão, as notas das 450 execuções vieram de um verificador de IA, calibrado em casos de resposta conhecida; nenhuma pessoa refez essas notas.
  • Cinco rodadas por combinação: a extensão descreve, sem teste de significância.
  • Mede se o agente aplica o pattern, e não se isso facilita as mudanças seguintes.
Dizer as limitações com naturalidade.
conclusão

Para quem escreve orientações para agentes de programação

  • Um arquivo curto de princípios, sem nomear patterns, já mudou o design (67% → 93%).
  • Uma skill com instrução de uso acrescentou mais na manutenção; sem a instrução, não foi aberta.
  • Vale vigiar o exagero e as outras dimensões: a estrutura desnecessária e o comportamento também mudaram.
  • Uma execução isolada não basta: o resultado se repetiu em 82% das repetições.
